§Module solver::spec

External, serialisable DTO describing which integration method to build and with what parameters — the HOW-axis config-loading increment of DT-027 amendment 1 (issue #104).

§Not IntegratorKind

IntegratorSpec is deliberately a separate type from super::IntegratorKind. The latter is a pure descriptive label, already carried by super::SolverConfiguration and super::snapshot::SimulationSnapshot — it is never consumed to build a solver. IntegratorSpec exists specifically to be consumed: TryFrom<IntegratorSpec> for Box<dyn Solver> bridges it to the existing BackwardEulerSolver builder, with no duplicated construction logic. Naming history: this type was called SolverConfig in issue #104’s original body — renamed before implementation to avoid colliding with super::SolverConfiguration, which already covers the full HOW pole (TimeConfiguration + calculators); see #104’s closing comment for the rationale.

§Scope

IntegratorSpec::BackwardEuler, IntegratorSpec::CrankNicolson (#115), and IntegratorSpec::BDF2 (#116, sparse fields since #133), covering the DA-043 (#50) sparse dispatch path — this whole module is gated behind the sparse feature: without it, a config DTO for these integrators adds nothing over the existing super::IntegratorKind labels, since the dense path takes no parameters. The explicit integrators (ForwardEulerSolver, RK4Solver, DoPri45Solver) take none either — the tolerances of DoPri45Solver belong to super::StepControl — so their IntegratorKind label describes them fully and IntegratorSpec has no variant for them.

The WHAT axis has its own specs since #108: DomainSpec builds a Domain from a MeshSpec, a ModelSpec, its BoundaryConditionSpecs and an optional InitialStateSpec, each in the module of what it describes. newton_convergence/jacobian_strategy/max_iterations (DD-044, #114/#115/#116) extend all three variants — the Newton configuration is orthogonal to which integrator carries it.

The sparse backend itself is always FaerSparseSolver — a fixed, non-configurable choice: Box<dyn SparseLinearSolver> is a trait object and cannot be deserialised, so there is no way for a config file to name an arbitrary backend (see #104’s discussion of this constraint).
